# dev-doc

### 这个 Skill 是什么？

把一个开发需求写成标准三段式开发文档的流程与格式规范。核心理念：**现状用真实数据说话，目标精简，计划只写大概但验收标准可执行**。

### 什么时候使用？

用户说"写个开发文档 / 需求文档"，或描述了一个需求并希望先文档后编码时。

### 产出位置与命名

- 路径：项目 `docs/` 目录
- 文件名：`YYYYMMDDHHMM-需求文档-<功能名>.md`
- H1 标题要有描述性，一句话带出：模块 + 改什么 + 从哪到哪。
  例：`命令配置 vlan batch 改造：从规范全集改为按设备实际承载的业务块生成`

### 写作流程（先调查，后落笔）

1. 先读相关代码，搞清现状的取数/执行链路。
2. 能查数据库就查数据库，拿**真实数据**做例子（真实表行、真实设备名、真实输出），不要编造示例。
3. 与用户确认期望的输出样子（"数据是什么样 → 我们要输出什么样"），再写文档。

### 三段式结构

**一、现状**

- 问题先行：第一段直接说现在的行为是什么、为什么不对，不要先铺垫架构。
- 用真实数据展示：贴出关键表的真实行（挑两三个有代表性的实例，覆盖差异面），
  让后来的人不用翻代码、翻会话就看懂为什么要开发这个功能。
- 给"现状输出 vs 实际需要"的对比块（代码块 + 行尾 `←` 注释）。
- 末尾用一行括号尾注交代取数链路（函数调用链），细节降级、不展开。
- 最后列出问题点（两三条，每条一句话）。

**二、目标**

- 精简：一句核心语义 + 几条规则 bullet + 一行预期结果。
- 规则里要包含"不变项"（non-goals 性质）：哪些保留、哪些不动（如模板语法不变）。
- 预期结果引用现状里的真实实例（同一批设备/数据），前后呼应。

**三、开发计划**

- 只写大概：每步写"达成什么效果 + 预计改哪个文件的哪些函数（新增/修改/删除）"。
  不写函数签名、入参出参、实现细节——那些必然漂移，留给代码表达。
- 颗粒度原则：计划详细程度与改动风险成正比；小改动三步以内。
- 步骤排序保证每步完成后代码库是绿的、可独立提交（纯函数先行 → 切装配点 → 回归交付）。
- 每步两个子节点：**改动**（文件 + 函数级落点）与 **验收标准**（可执行断言：
  具体输入→具体输出、具体文件的具体行、具体命令全绿；优先用现状里的真实数据做断言）。

### 格式规范

- 开发计划用大纲笔记形式：有序列表步骤 + 嵌套 bullet。
- 缩进 4 个空格。
- 每个 bullet 之间空一行。
- 加粗只用在"开头"：步骤名加粗、`**改动**`/`**验收标准**` 小标题加粗；行内文字不加粗。
- 中文句子里一律用全角标点（，：（）；），不用 ASCII 半角。
